Two environments matter, and they are not the same machine.

## 1. What I could inspect directly (the sandbox I run in)

I executed this audit in the container where I edit your repository. **It is not
your Windows PC.** Recording it matters anyway, because it tells you exactly what
I could and could not verify before handing work back.


### What that means, concretely

| Capability | Available here? | Consequence |
| --- | --- | --- |
| Run Python, install from PyPI | yes | The whole PC side is testable |
| Run protocol and end-to-end tests | yes | 45 tests, all passing |
| Compile Kotlin / build the APK | **no** | Gradle would need a JDK *and* the Android SDK (dl.google.com is not reachable from here) |
| Run an emulator or a real phone | **no** | Any Android-side claim is "written and reviewed", never "observed working" |
| Touch WASAPI, virtual audio, cameras | **no** | Windows integration is designed and specified, not executed |
| Use a Bluetooth radio | **no** | Every SCO/HFP statement carries the platform constraint behind it and is marked `[needs device]` |

This is why Phase 1 was verified against a **reference implementation of the
phone** (`tools/simulator/phone_sim.py`) rather than being declared done. The
simulator speaks the identical wire protocol, so the PC client, the crypto, the
pairing flow, the reconnection logic and the discovery listener are all genuinely
exercised. The Kotlin port is checked against known-answer vectors generated by
the Python implementation, which is the strongest cross-language check available
without a device.

## 2. What I need from your machine

Run the audit script on your Windows PC:

```powershell
cd phone-bridge
powershell -ExecutionPolicy Bypass -File tools\diagnostics\env_report.ps1
```

It is read-only. It reports Windows build, Python, JDK, Android SDK, adb, audio
endpoints (including whether a virtual cable is installed), camera devices, OBS,
Bluetooth radios and headsets, firewall state for the ports PhoneBridge uses,

below and adjust the Phase 2 plan to your actual hardware.

## 3. Known environment risks, and the mitigation for each

| Risk | Mitigation already in place |
| --- | --- |
| No JDK on the PC → cannot build the APK | Install Android Studio (bundles JDK 17 + SDK), or `winget install Microsoft.OpenJDK.17` + command-line tools |
| Windows Firewall blocks the discovery beacon or an inbound test | Only UDP 47823 inbound is needed, and only for discovery; outbound TCP 8765 to the phone is always required |
| `adb forward` breaks when adb restarts | Use USB tethering for anything long-running; adb is a development convenience only |
| Wi-Fi access point with client isolation | Hotspot mode, USB tethering, or manual IP entry all bypass it |
| Company-managed PC blocking driver installation | PC → phone audio needs **no** driver; only the microphone direction needs a virtual cable |
